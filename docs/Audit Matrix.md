# FedACT Pre-Experiment Audit Matrix

> **Exact requirement count:** **250**
>
> **Scope:** Pre-experiment verification only. This matrix must be executed before any development or confirmatory scientific `fedact run <workflow>` workload. It permits repository inspection, fresh Graphify analysis, static/type/architecture checks, targeted tests, short read-only commands, production preprocessing, and the genuine implementation-only smoke workflow.
>
> **Scientific authority:** The FedACT Authoritative Research Roadmap is binding for formulas, chronology/information restrictions, experiment design, metrics/statistics, seed roles, claim/failure semantics, and evidence requirements. Observed dataset properties may legitimately amend historical expectations when backed by acquired-data evidence. Internal file/module structure is implementation-flexible when the scientific contract is preserved.
>
> **Generation note:** This matrix was generated from the full supplied FedACT roadmap and its declared repository/CLI contract. It does **not** represent a completed audit of the current repository; `Status` and `Finding / Action` are intentionally blank until an auditor executes each requirement against the working tree.

## Purpose and Scope

This file is the execution checklist for deciding whether FedACT is scientifically and technically ready to begin its experiment program. It is deliberately pre-outcome: it verifies scientific semantics, mathematics, chronology, data preparation, workflow registration/wiring, reproducibility, statistics, domain typing, artifacts, and evidence-generation paths without running claim-bearing experiments or tuning against experimental outcomes.

The eventual auditor must use the current working tree as the implementation authority, the roadmap as the scientific authority, and real acquired data as the authority for observed schema/count/support facts. A mismatch in file layout or helper names is not a defect by itself. A mismatch in scientific meaning is.

## Authority Hierarchy

| Authority class | Audit rule |
| --- | --- |
| Scientifically authoritative | Formulas, inequalities, algorithms, information restrictions, chronology, experimental design, methods/comparators, grids, metrics, statistical units/methods, multiplicity, seed roles, claim/failure semantics are binding unless the roadmap explicitly allows variation. |
| Empirically amendable | Actual client/cohort/sample/family/campaign counts, usable time spans, observed schema, support, runtime/hardware properties, and unavailable secondary conditions may differ when the real acquired data prove the deviation. Record the evidence and resulting eligibility effect; never manipulate data to recover an obsolete estimate. |
| Implementation-flexible | File names, module boundaries, helper/class names, internal architecture, library choice, caching/parallelization strategy may differ if semantics, reachability, determinism, and evidence contracts are preserved. |

## Status and Severity

`Status` is left blank until the audit is executed. Once evaluated, use only: `PASS`, `FAIL`, `PARTIAL`, `MISSING`, `UNWIRED`, `DEAD_CODE_CANDIDATE`, `JUSTIFIED_EMPIRICAL_DEVIATION`, `JUSTIFIED_ARCHITECTURE_DEVIATION`, `BLOCKED_BY_PRE_EXPERIMENT_STATE`, `NOT_APPLICABLE`.

Severity values are `BLOCKER`, `MAJOR`, and `MINOR`. A status is not a severity: for example, a justified empirical deviation may be a PASS-equivalent scientific resolution even when the roadmap expectation differed.

## Audit Execution Order

Execute the matrix in this order: roadmap/repository inspection → actual CLI inventory → first fresh Graphify → callable/workflow inventory → science/math/preprocessing/experiment-contract/statistics/type/architecture/artifact audits → remediation → second fresh Graphify → static/architecture checks → tests → permitted short commands → real preprocessing → deterministic/idempotent preprocessing rerun → smoke → final fresh evidence review → **stop before scientific experiments**.
